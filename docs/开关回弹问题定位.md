# 开关"按下即回弹"问题定位（bt / leds 开关）

> 现象：屏幕单独调试时，bt 与 leds 的开关键可以正常开关；
> 接上 ESP32 后，其他交互都正常，**唯独这两个开关按不下去**——
> 一按开就立刻弹回关，且（屏幕上）没有数据回传给音箱。
>
> 本文只做问题整理与判别，**不含修复**。取证用的日志开关已临时打开（见文末）。

---

## 一、先看一个硬事实：屏幕上那个开关的显示状态，只有一个"写者"

在 `main/ui.c` 里，能把开关控件状态写回屏幕的，**只有音箱**，共两个函数：

| 函数 | 写什么 | 什么时候写 |
| --- | --- | --- |
| `ui_push_led_switch()` | `n0.val=1/2` + `b0.picc=14/18` | ①切到 leds 页/每次收到 `leds`（`ui_refresh_page`）②`ledon`/`ledoff`/`n0.val=1/2` 执行完之后 |
| `ui_push_bt_switch()` | `n0.val=1/2` + `b0.picc=7/6` | ①切到 bt 页/每次收到 `bt` ②`bton`/`btoff`/`n0.val=1/2` 执行完之后 |

音箱侧**没有**任何定时/周期推送（`ui.c` 里没有周期任务）。所以：

> **"回弹"这一现象本身必然来自音箱的这条推送**——按开的瞬间屏幕上短暂显示"开"，
> 紧接着音箱推了一条"关"把它盖掉。音箱推"关"只有一个原因：**音箱内部状态此时仍然是"关"**。

也就是说：**那次"按开"的音箱侧动作没有生效**。剩下要查的就是"为什么没生效"——
是屏幕没发、还是发了被音箱丢掉。

---

## 二、音箱侧可能造成"没生效"的 3 个位置（读源码确认，按可能性排序）

### 音箱侧可疑点 1：`n0.val` 是唯一"按页面判定"的开关命令，页面未知时会被静默丢弃

`main/ui.c` 第 240~254 行：

```c
if (ui_attr_int(ui_res, "n0.val", &val)) {
    if (s_page == UI_PAGE_LEDS)        { ... 开/关灯带 ... }
    else if (s_page == UI_PAGE_BT)     { ... 开/关蓝牙 ... }
    else {
        ESP_LOGW(TAG, "收到 n0.val=%d，但当前页面未知（%s）："
                      "无法判断是灯带开关还是蓝牙开关，已忽略", val, ui_page_name(s_page));
    }
    return;
}
```

`n0` 在 leds 与 bt 页同名，只能靠"当前页面"区分，所以页面状态一旦丢失（页面名没收到、
`exit` 之后没等到页面名、休眼误判等），这条命令就**什么都不做**。

- **与现象吻合度：高**。其它命令里，`led1/led2`、`bton/btoff/btpla/btpau/btne/btla`、
  `R/G/B`、`V` 都是**与页面无关**的，只有开关(`n0.val`)、`n2.val`、`h*.val` 依赖页面。
  "唯独两个开关不行、其他都行"正好是这个特征。
- **日志指纹**：`收到 n0.val=1，但当前页面未知（unknown/...）：...已忽略`
- **前提**：你的开关发的是 `n0.val=1/2`（而不是 `ledon`/`bton`）——
  这一点你前后两次描述不一致，需要确认（见第四节问题 1）。

### 音箱侧可疑点 2：蓝牙开关有 1 秒防抖，第二次按会被直接吃掉且不回推状态

`main/ui.c` 第 822~858 行，`BT_SWITCH_DEBOUNCE_MS = 1000`：

```c
static void cmd_bt_on(void) {
    if (!ui_bt_switch_allowed()) {
        ESP_LOGW(TAG, "蓝牙开关命令过于频繁（< %d ms），忽略本次开启", BT_SWITCH_DEBOUNCE_MS);
        return;                 /* ← 直接返回，不执行、也不推状态 */
    }
    ...
}
```

- **与现象吻合度：中**。"关→开"两次按得较快（<1 s）时，"开"被丢掉，状态仍是关，
  下一次刷新就把开关弹回关。
- **日志指纹**：`蓝牙开关命令过于频繁（< 1000 ms），忽略本次开启`
- 注意：**灯带开关没有防抖**，所以如果你测出"两个开关同时不行"，这一条解释不了灯带，
  说明还有一个共同原因（即可疑点 1 或第三节的屏幕侧原因）。

### 音箱侧可疑点 3：`b0.picc` 可能改错属性 / 图号不存在

你之前抓到的 `04 FF FF FF`（=图片ID无效）有两种可能的来源：①屏幕工程自己的事件代码；
②**音箱发的 `b0.picc=14/18/7/6`**。如果 `b0` 恰好就是那个开关控件本身
（双态按钮的图片是用 `picc/picc1` + `val` 表现的），那么：

- 我们发 `n0.val=1/2` 改的可能是**另一个控件**（或不存在 → `02`）；
- 我们发 `b0.picc=xx` 改的是**这个按钮的图片属性**，而不是它的"选中状态"。

这种情况下开关的显示不会按预期走，甚至在收到状态刷新后回到旧的图片外观。
**需要你确认 `b0` 的控件类型与图号**（见第四节问题 3）。

## 三、屏幕侧可能造成"没回传数据"的 3 种写法

### 屏幕侧写法 A：开关事件里只做了"视觉赋值/跳页"，没有真正 `prints`

例如弹起事件写成了：

```
// 弹起事件
n0.val=1            // 或 b0.picc=14
page leds           // ← 重进本页（或整页刷新）
```

在屏幕单独调试时，**没有音箱**来重推状态，页面重进后按页面里的初始值显示，
看起来"能开关"；接上音箱后，页面重进 → 屏幕发 `leds`（页面名）→ 音箱补发
`n0.val=2` + `b0.picc=18`（音箱侧状态是关）→ **开关立刻弹回关**，
而屏幕自始至终没有发过开/关命令 → **"没有回传数据"**。

- **与现象吻合度：很高**（三个现象同时满足：能按、立刻回弹、无数据）。

### 屏幕侧写法 B：发的是别的字符串，音箱词表里没有

例如发 `led_on`、`ON`、`LED1`、`开关` 之类。音箱会打印 `未知命令: "xxx"`（**会在日志里看到**）。

### 屏幕侧写法 C：`n0.val` 的"值语义"与音箱约定相反

你约定的是 `n0.val=1 → 开`、`2 → 关`。如果屏幕工程里把 1/2 写反了（例如图片 `picc`
对应关系反了、或 `n0.val` 实际是 0/1 而不是 1/2），那么按下"开"时音箱收到的是"关"，
音箱执行关 → 推 `n0.val=2` → **屏幕上就是"按开立刻弹回关"**。

- **与现象吻合度：中高**（"无数据"这一条不符合，除非你没注意到日志里有数据）。
- 需要确认：屏幕开关控件 `n0` 的 `maxval/minval` 与两个状态的实际取值。

## 六、结论（当前证据下的判断）

- "按开立刻回弹"**只能是音箱这条状态推送造成的**（屏幕侧没有第二个写者）——
  这一行为本身是设计使然（音箱是开关状态的权威），**不是 bug**。
- 真正的问题是"**那次按开没有让音箱的状态变成开**"。它有两种可能：
  - **屏幕侧**：按压事件没有真正把命令发出来（只做了视觉/跳页），或发的字符串/取值
    与约定不一致 → 现象里"没有回传数据"支持这一条；
  - **音箱侧**：命令发出来了，但被"页面未知静默丢弃"（可疑点 1）或"蓝牙 1 秒防抖"
    （可疑点 2）吃掉 → 这两种情况日志里**一定留有对应警告**。
- 因此**只要拿到第五节的日志，就能一次性定性**。在此之前，从"其他交互都正常、唯独
  两个开关不行、且没有回传数据"这三个现象看，**屏幕侧（写法 A：事件里只做视觉赋值/
  重进页面，没有 prints 命令）的可能性更大**；音箱侧最需要排查的是可疑点 1
  （`n0.val` 在页面未知时被丢弃）与可疑点 2（蓝牙 1 秒防抖）。

# 七、已确认根因（本轮日志与屏幕源码证据）

## 7.1 你的开关代码是一个"自增计数器状态机"

```c
n0.val++
if(n0.val==1)      { b0.picc=14 ; prints "ledon",0 }
else if(n0.val==2) { b0.picc=18 ; prints "ledoff",0 ; n0.val=0 }
```

它隐含的状态含义是：

| `n0.val` | 含义 |
| --- | --- |
| **0** | 关（就绪，下一次按 = 开） |
| **1** | 开（下一次按 = 关） |
| **2** | 关（**瞬时值**，代码自己立刻把它复位成 0） |
| **≥3** | **没有任何分支处理 → 按下去什么都不做（不发数据、不改图片）** |

注意：**代码自己把"关"写成 `n0.val=0`**（`else if` 分支里的最后一句），
也就是说这套状态机里"关"的正确值是 **0**，`2` 只是一个中间过渡值。

## 7.2 音箱写的是"绝对状态 1/2"，正好把计数器打到 3 以上

上一轮按你的要求，音箱在**切页/状态变化**时推：

```
n0.val=1   （开）  + b0.picc=7/14
n0.val=2   （关）  + b0.picc=6/18
```

于是计数器被污染：

| 音箱推入 | 你按一次 → `n0.val++` | 进入哪个分支 | 结果 |
| --- | --- | --- | --- |
| `n0.val=2`（关） | **3** | 都不进 | **不发数据、不改图片 → "按了没反应、看起来回弹到关"** |
| 继续按 | 4、5、6… | 都不进 | 永久失效，直到页面重进把 `n0` 复位 |
| `n0.val=1`（开） | **2** | `==2` | `prints "ledoff"` + 复位 0 ✔ 正常 |

**所以：只要音箱把 `n0.val=2` 写进去，这个开关就彻底按不动了**——
而"关"恰好是上电默认状态、也是切进 leds 页时的状态，所以表现为"这个开关从来打不开"。

## 7.3 日志逐条对上（这就是铁证）

你的验证流程：进 leds → 多次点 ledon → 退出 → 进 bt → 点关蓝牙 → 多次点开蓝牙。

| 日志 | 时间 | 说明 |
| --- | --- | --- |
| `解析指令: "leds"` → `TX→屏幕: "n0.val=2"` + `"b0.picc=18"` | 20978 | **进 leds 页时音箱把 2 写进了计数器 → 计数器从此从 3 开始** |
| （20978 ~ 37668 之间**完全没有** `解析指令: "ledon"`） | | 你"多次点击 ledon" **一次都没发出来** ← 因为 `n0.val++` 得到 3、4、5… 不进任何分支 ✔ 与 7.1/7.2 完全一致 |
| `解析指令: "exit"` → `"main"` | 37668/37728 | 退出 leds |
| `解析指令: "bt"` → `TX: "n0.val=1"` + `"b0.picc=7"` | 38328 | 进 bt 页时音箱写 **1**（因为蓝牙上电即开） |
| `解析指令: "btoff"` | 41488 | 点"关闭蓝牙" → `1++ = 2` → **命中 `==2` 分支 → 正常发出 btoff** ✔ 所以"关"是好用的 |
| `TX→屏幕: "n0.val=2"` + `"b0.picc=6"` | 41558 | 关蓝牙后音箱又写 **2** → **计数器再次被污染** |
| （41558 之后**再也没有** `解析指令: "bton"`） | | 你"多次点击打开蓝牙" **一次都没发出来** ← `2++ = 3、4、5…` ✔ 与 leds 现象同源 |

两个界面的现象是**同一个原因**：都是"音箱写入 2 → 计数器 ≥3 → 开关死掉"。

## 7.4 结论：责任划分

- **屏幕侧**：开关事件用的是"自增计数器 + 只处理 1/2"的写法。它假设 `n0.val` 只由自己维护
  （0→1→2→0），**不能接受外部把 0/1 之外或"过渡值 2"写回来**。这是现象的**根本原因**；
  它在屏幕单独调试时看不出来，正是因为那时没有外部写者。
- **音箱侧**：写"绝对状态 2"是**触发条件**。按你最初的要求（`n0.val=1/2` 表示开/关）
  实现并没有错，但它与你屏幕代码的真实取值语义（**0=关、1=开、2=瞬时过渡**）不一致。
- 一句话：**是一个"取值语义约定不一致"的问题，根因在屏幕的自增写法，音箱侧的写入是导火索。**

# 八、闭环证据：`btoff` 那一条日志本身就是"判决书"

你的屏幕代码（弹起事件）与 `n0` 默认值 0 都成立，代码在**单独接串口助手**时也确实正确工作。
下面这条推理不需要任何新实验，就能把"是不是音箱写坏了计数器"证死。

## 8.1 状态机在两种环境下的走法

| 环境 | 进页面时 `n0.val` | 按一次（`n0.val++`） | 命中分支 | 是否发数据 |
| --- | --- | --- | --- | --- |
| **只接串口助手**（音箱不写） | 0（页面默认） | 1 | `==1` | 发 `ledon` ✔ 你已实测 |
| 再按 | 0（代码自己复位） | 1 | `==1` | 发 `ledon` ✔ |
| 想发 `ledoff` | 1（上一次按下后是 1） | 2 | `==2` | 发 `ledoff` + 复位 0 ✔ |
| **接 ESP32**：进 leds 页时音箱写 `n0.val=2` | **2** | **3** | 都不命中 | **什么都不发** ✘ |
| 继续按 | 3 | 4 | 都不命中 | 什么都不发 ✘ |

## 8.2 `btoff` 这一条为什么是"判决书"

进 **bt 页**时，音箱推的是 `n0.val=1`（因为蓝牙上电即开，`bt_a2dp_is_on()==true`）。
随后你按了一次"关闭蓝牙"，ESP32 日志里出现的是：

```
I (41488) UI: 解析指令: "btoff"
```

请对照 8.1 的表格：

- 若音箱那次 `n0.val=1` **没有**写进屏幕 → 进入弹起事件时 `n0.val` 仍是页面默认值 **0** →
  `0++ = 1` → 命中 `==1` 分支 → 屏幕会发 **`bton`**（开），**绝不可能发 `btoff`**。
- 实际发出的是 **`btoff`** ⇒ 弹起事件里 `n0.val` 当时是 **1** ⇒ **音箱写的 `n0.val=1` 确实写进了屏幕的 `n0`**，
  并且**写进去的值直接决定了这一次按下的动作**。

既然写入生效、且取值决定动作，那么同一段代码里"进 leds 页写 `n0.val=2`"就必然把计数器推到 **3**，
于是"多次点击 ledon、ESP32 一条 `ledon` 都收不到"（日志 20978~37668 之间确实一条都没有）。
两个界面、两种现象，同一条因果链，全部对上。

## 8.3 所以"屏幕代码有没有问题"

- **单独看：没有问题**。`0→1→2→0` 这套自增循环在"没有外部写者"时是自洽的，
  串口助手实验也证明了这一点。
- **和音箱一起看：存在一个约定冲突**——你的状态机里 `n0.val` 是**计数器**，
  取值含义是 `0=关(就绪)`、`1=开`、`2=**只由自己产生的瞬时值**`；
  而音箱按最初的需求把 `2` 当作"关"的**静止值**写回去。
  计数器可以被"喂"0 或 1，但**不能被喂 2**——喂 2 之后下一次自增就是 3，永远不进分支。
- 换句话说：**不是谁的代码"错"，是"关"这个状态的编码在两处不一致**
  （你的代码用 `0` 表示关，音箱用 `2` 表示关）。而且**你的代码自己就把"关"写成 `n0.val=0`**，
  这正好说明：外部刷新"关"时应该写 **0**。
