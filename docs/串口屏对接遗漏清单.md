## 5. 本次顺带发现并已修掉的问题（仅供参考，不用回复）

1. **关灯后再次开关灯无响应**（任务 2 的 bug）——三个原因：
   - `ledon` 映射到 `leds_init()`：RMT 通道已存在，同引脚二次创建失败 → 断言复位；
   - `leds_reon()` 先 `update_led()` 再 `rmt_enable()`：向**已关闭**的通道发数据 → 断言复位；
   - `led_mode` 彩虹灯效用嵌套 `while(1)` 死循环，关灯后仍每 50ms 刷灯 → 断言复位。
   现在开关由 `leds_on()/leds_off()`（调度级）+ 状态守卫统一管理，彩虹灯效改为可被打断的单层循环。
2. **`vTaskSuspend(NULL)` 会挂起调用者自己**：`bt_sleep()` 在“未连接手机”时 `s_bt_i2s_task_handle == NULL`，
   一旦按“暂停”就会把**正在分发串口屏命令的 ui_task** 自己挂起 → 串口屏全部命令永久无响应。已加判空。
3. **`bt_con_flag` 断开后不清零**：导致后续“关蓝牙”对已卸载的 I2S 通道重复反初始化 → 断言复位。已清零，并给 I2S 安装/卸载加了幂等保护。
4. **同一条命令被重复处理 / 响应慢**：旧主循环每 500ms 才 `process_command()` 一次，且 `memset` 在调用之后（同一命令会被处理两次）。现改为“rx_task 断帧 → 队列 → ui_task”即时分发。
5. **`ui_res[10]` 太小 + 过滤器删掉 `= . "`**：会把 `b0.val=100` 这类陶晶驰属性回传截断/破坏。已扩到 32 并保留完整可打印 ASCII。
6. **AVRCP 元数据 `medata_flag` 恒为 0**：导致任何属性（专辑/流派…）都会覆盖曲名 `t2.txt`。已按属性号 0x1=曲名、0x2=歌手 分发。
7. **电量 200ms 无脑刷屏**：旧 `rx_task` 每 200ms 发一次 `ba.val`（不管在哪一页，非法控件会回错误码）。现改为“切页补发 + 数值变化才发”。
8. **`bt_ne()/bt_la()` 是空函数**（只打日志），上/下一首按钮实际无效。已补 AVRCP `FORWARD/BACKWARD` 透传。
9. `bt_app_task_start_up()` / `bt_i2s_task_start_up()` 重复调用会重复建任务与 32KB 环形缓冲区（关蓝牙再开时发生）。已加幂等。

## 6.10 本轮修复：文本命令与返回码"粘连"导致命令丢失

**现象**：`leds` / `ledon` / `ledoff` 无法解析，而 `bt` / `btoff` 正常。

**原因**：屏幕的错误返回帧（`04 FF FF FF` = 图片ID无效）非常密集，而屏幕发文本命令用的是
`prints`（**不带帧尾**）。当两者挤在同一次串口读取里时，字节流形如

```
6C 65 64 73 04 FF FF FF     →  帧体 = "leds" + 0x04
```

旧实现看到帧体里含不可打印字节，就整帧判成"二进制返回码"并丢弃，于是那条命令凭空消失
（`bt`/`btoff` 恰好单独到达，所以能正常解析）。

**修复**：`main/uart.c` 的 `handle_frame()` 现在按四步判定，混合帧不再丢命令：

1. 全可打印 → 文本命令；
2. `ASCII属性名 + 小端二进制数值`（`prints "h0.val=",0` + `prints h0.val,0`）→ 还原成文本；
3. 标准返回码结构（0x65/0x66/0x67/0x70/0x71/0x86~0x88/0x00~0x24…，**连长度一起判断**，
   因此不会把 `exit` 误判成 0x65）→ 按返回码处理；
4. **混合帧 → 前面的文本照常分发，后面的返回码单独处理**，并打印
   `帧内混有文本与返回码：先当命令解析 "leds"，再处理返回码 0x04`。

**顺带**：新增 0x86/0x87 支持——屏幕自动上报的"进入睡眠/自动唤醒"比 `exit` 超时判定更可靠，
收到即切换休眠状态（`exit` 1.5 s 超时仍作为兜底保留）。

> 关于满屏的 `0x04 FF FF FF`：它是屏幕报"**图片ID无效**"，属于屏幕工程自己的问题，
> 与本机命令无直接关系。常见来源有两个：
> ① 屏幕页面/定时器事件里给某个控件赋了不存在的图片号（例如 `x0.picc=6` 但图片资源里没有 6）；
> ② 本机发的 `b1.picc=6/7`（蓝牙页播放/暂停图标）与屏幕 `b1` 的实际切图号不匹配。
> 请按日志里出现的时机核对；需要我把 `b1.picc` 换成别的值（或改成 `vis` 显隐控制）告诉我即可。
## 6.11 本轮修复：忽略 0x04 + 三种"粘连/夹带"形态全部兼容

### ① `04 FF FF FF` 静默忽略

`main/uart.c` 的 `handle_binary_code()` 开头：**0x04（图片ID无效）不处理、不打印**，
直接从字节流跳过继续解析后面的真实命令。

不打印还有关键副作用：原 WARNING 日志会占用串口输出时间，错误帧密集时会把接收环形缓冲区
冲溢出、导致**真实命令丢字节**。现在静默后不再占用。UART 接收环形缓冲区同时从 512 B 加大到 **1024 B**。

> 排查图片号问题时把日志级别调到 DEBUG，可见 `忽略返回码 0x04（图片ID无效…）`。

### ② 实际抓到的字节流与处理结果

| 屏幕实际发送 | 帧体 | 处理 |
| --- | --- | --- |
| `04 FF FF FF` | `04` | 静默忽略，继续解析 |
| `04 FF FF FF` + `04 FF FF FF` + `62 74 6F 6E` | `04`、`04`、`bton`（无帧尾，靠 30 ms 空闲断帧） | 两次忽略 → `bton` 正常执行 |
| `6C 65 64 6F 6E 04 FF FF FF` | `ledon` + `04`（**文本在前**） | 取出文本段 `ledon` 执行；`04` 忽略 |
| `04 6C 65 64 6F 6E FF FF FF` | `04` + `ledon`（**返回码在前**） | 前段按返回码忽略；文本段 `ledon` 照常执行 |
| `6C 65 64 6F 66 66 04 FF FF FF` | `ledoff` + `04` | 取出 `ledoff` 执行 |
| 多条文本粘成一条（`ledsledon`） | 全可打印 | ui.c 词表重同步最长匹配拆分后逐条执行 |

即：**只要帧体里存在可打印文本段（≥2 字节），就一定会被取出来当命令执行**，
不可打印部分一律交给返回码处理（0x04 静默）。三种形态——纯文本、文本+返回码、返回码+文本——
以及文本互相粘连，全部兼容，屏幕工程不需要改动。

### ③ 开关状态补发增加切图

| 页面 | 开 | 关 |
| --- | --- | --- |
| **bt** | `n0.val=1` + `b0.picc=7` | `n0.val=0` + `b0.picc=6` |
| **leds** | `n0.val=1` + `b0.picc=14` | `n0.val=0` + `b0.picc=18` |

两处都在"切页补发"和"开关状态变化"时发送（同一个 `ui_push_bt_switch()` / `ui_push_led_switch()`）。
